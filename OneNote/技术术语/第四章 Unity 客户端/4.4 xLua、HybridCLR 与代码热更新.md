# 4.4 xLua、HybridCLR 与代码热更新

> 例子：xLua 是让 C# 和 Lua 互相说话的翻译；pUerts 是让 C# 和 JavaScript／TypeScript 互相说话的翻译；HybridCLR 则让正式包里还能运行后续下发的新 C# 程序集。它们都能让活动和逻辑改动不必每次重新上架整包。

> 一句话：xLua 用 Lua 写逻辑，**pUerts 用 TypeScript／JavaScript 写逻辑**，HybridCLR 用 C# 热更；三者都是游戏代码热更新的常见方案，但实现方式不同。

## pUerts（常被误写成 purats）

### 说人话

pUerts 是腾讯开源的脚本桥接方案：**游戏底层和性能敏感部分继续用 C#／C++ 写，活动、UI、任务等经常改的逻辑可以用 TypeScript 写**。项目更新时，下发新的脚本文件即可，通常不必为了改一段活动逻辑重新发整个安装包。

### 在 Unity 里通常怎么用

- Unity／C#：角色底层能力、渲染、资源、网络等相对稳定的部分。
- TypeScript：活动、UI、任务、配置驱动玩法等变化频繁的部分。
- pUerts：负责让两边互相调用，例如TS调用Unity角色接口，或C#通知TS更新UI。

> pUerts 本身是“翻译层”，并不自动解决版本管理、脚本下载、灰度和回滚；这些仍需要项目自己的热更新与发布系统配合。

### 和 xLua、HybridCLR 的区别

| 方案 | 主要写什么语言 | 更适合什么情况 |
|---|---|---|
| xLua | Lua | 团队已有Lua体系，轻量脚本与活动逻辑较多 |
| pUerts | TypeScript／JavaScript | 团队想用TS，或希望前端背景开发者也能参与游戏逻辑／UI开发 |
| HybridCLR | C# | 希望仍完全用C#开发热更新代码，不想维护第二种脚本语言 |

### 看简历时怎么判断

简历写“会pUerts”只能说明接触过TS与Unity互通；不等于真正负责过热更新框架。可以追问：

1. TS实际做了哪些模块，是UI、活动还是核心玩法？
2. 脚本如何下载、加载、版本校验和回滚？
3. 是否处理过TS与C#互调、性能、内存或线上脚本问题？
4. 是否建设过调试、日志、代码规范或多人协作流程？

### 💡 猎头应用与常见排雷（补充）
- **简历搜索与匹配**：如果候选人简历中频繁提及 **xLua、HybridCLR 与代码热更新** 相关词汇，说明其参与了对应的技术模块或具备相应底层经验。
- **面试与沟通对齐**：不要仅停留在“是否了解该名词”，重点追问候选人在 **xLua、HybridCLR 与代码热更新** 方面的**实际落地项目**、**遇到过的性能/技术瓶颈**以及**最终的量化成果（如优化的帧率、减少的耗时）**。
- **避坑与定级指南**：许多初中级人员仅停留在“调包”或“在框架内填代码”的阶段。若是推荐大厂高职级或核心引擎组岗，务必核实其是否具备底层机制拆解、架构重构和从0到1搭框架的能力。
